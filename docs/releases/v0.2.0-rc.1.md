## Why the minor version changes

The candidate removes the Bonsai 2 llama.cpp runtime (PR #265). A stored
Setup or runtime manifest that names `runtime_flavor: "bonsai2-pq2"` no
longer loads; it fails with `unsupported llama.cpp runtime_flavor`. Remove or
migrate such manifests before upgrading. In the 0.x series this
incompatibility is signalled by the minor version, so the next release is
`0.2.0`, not `0.1.4`.

## Integrated changes since v0.1.3

1. **Strata runtime provider (PR #266, PR #267).** Strata serves
   Qwen3.6-35B-A3B on a single GTX 1080 Ti (64K context) and on deneb (12K).
   Schema-declared booleans in tool arguments are restored. The Worker refuses
   at startup a serving contract whose `total_tokens` differs from the Strata
   run context. See [Strata runtime](../runtime-strata.md).
2. **FreeToken chat backend for GTX 1080 Ti (PR #261, PR #263, PR #264).**
   Pinned installer, Gateway chat in a real Worker (serving features,
   tool-call shape, thinking control), and Worker permissions for production.
   FreeToken served spica and deneb before Strata replaced it. It remains
   available as a rollback path. See [FreeToken runtime](../runtime-freetoken.md).
3. **Bonsai 2 runtime removed (PR #265).** This is the breaking change above.
   `runtime_flavor` still exists and accepts only `"upstream"`. The
   `bonsai-llama-cpp` target of `astrumweaver-runtime-profile` exits with
   code 2.
4. **llama.cpp KV cache element types (PR #268).** `cache_type_k` and
   `cache_type_v` select `--cache-type-k/-v`, for example `q8_0` for a 192K
   context on two RTX 3060s. They are kept out of the dual (embedding plus
   decision) llama.cpp runtime.
5. **SSE keep-alive for long prompt reads (PR #269).** While a chat stream
   waits for its first chunk, the Gateway sends `: keep-alive` comments every
   `stream_keepalive_seconds` (default 15). Proxies in front of Control no
   longer cut streams during minutes-long prefills. Non-streaming requests
   still depend on the proxy timeout.
6. **Serving contracts checked against runtime context (PR #270, #262 item 4).**
   At startup the Worker refuses a llama.cpp chat contract whose
   `total_tokens` exceeds `--ctx-size`. It also refuses a FreeToken contract
   that exceeds `max_seq_len`, and a FreeToken `max_prefill_tokens` larger
   than `max_seq_len`.
7. **External VOICEVOX groundwork (#247 R1–R4-C2-A, PRs #248–#258) and audio
   provider assembly reviews (PRs #220, #222, #224–#226, #233, #236, #239).**
   These are source-only contracts and synthetic tests. **No audio engine is
   qualified or enabled by default.** Audio serving stays outside the release
   guarantee.
8. **CI:** runtime-module-eval no longer fails falsely on SIGPIPE (PR #228, #227).

## Production evidence (operator site, 2026-11-16)

The integrated source already runs in the maintainer's production site. This
evidence covers that site only; it is not a universal qualification.

| Host | Profile | Runtime | Build |
| --- | --- | --- | --- |
| Control | Gateway + scheduler | — | main `a8f6ac2` (PR #269) |
| spica | `qwen3.6-35b-a3b`, 64K | Strata 0.2.13.1 | main `bf5b086` |
| deneb | `qwen3.6-35b-a3b-short`, 12K | Strata 0.2.13.1 | main `bf5b086` |
| sirius | `qwen3.6-35b-a3b-fast`, 196608 | llama.cpp, KV `q8_0` | main `a8acfdc` (PR #270) |

Chat requests through Control and through the public endpoint (streaming)
returned 200 on every profile. The contexts above served real long prompts,
for example 19.5K tokens on spica and about 180K tokens on sirius. Embedding
and decision Workers stayed on the `v0.1.x` builds and are unaffected.

## Operational boundaries

- PostgreSQL 17 migrations `000`–`005` are unchanged since v0.1.3. No
  migration runs at release time.
- Publishing the tag or the GitHub Release does not update running services,
  credentials, model downloads or GPU ownership. Site rollout still needs an
  explicit operator GO with a rollback path.
- Historical release notes stay byte-for-byte unchanged. The release-version
  alignment tests pin them by SHA-256.

## Remaining publication steps

1. Merge the release PR and wait for the merge commit's CI to pass.
2. Build the wheel, sdist and source archive from the exact merge commit, and
   write `RELEASE-MANIFEST.txt` and `SHA256SUMS`.
3. Create the annotated prerelease tag `v0.2.0-rc.1` and publish the GitHub
   prerelease with those assets.
4. Promote to `v0.2.0` GA by changing version metadata only, after the
   maintainer accepts the candidate.
