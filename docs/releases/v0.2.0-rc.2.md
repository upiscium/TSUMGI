## Why a second candidate

A practical trial of rc.1 with OpenCode 1.18.35 on 2026-11-17 found three
problems on the serving path. Answers were correct, but the sessions were slow
or failed under ordinary use. This candidate fixes all three.

## Changes since v0.2.0-rc.1

1. **Streamed chunks are coalesced on the Worker (PR #272).**
   - Before: every streamed chat chunk was its own fenced Control RPC, awaited
     by the executor. Delivery was capped at about 10 tokens/s on every
     profile, whatever the decode speed.
   - Now: a Worker keeps one event publish in flight. Text deltas, and
     argument fragments of the same tool call, that arrive meanwhile merge
     into the next event. That event is still an ordinary OpenAI chat chunk.
   - Unchanged: finish, usage and role chunks are never merged. Content and
     reasoning never share an event. All events are published before the
     terminal write.
2. **Pre-stream failures are HTTP errors (PR #273).**
   - Response headers now go out with the first chunk or the first
     `: keep-alive`.
   - A Job that fails before that gets the same JSON error and status as the
     non-streaming path. For example, context overflow is 400
     `context_length_exceeded`, a gateway timeout is 504, and an invalid
     backend stream is 502.
   - Why it matters: OpenCode compacts a session only on such an HTTP error.
     An in-stream error frame is retried and then fails the session.
3. **Bounded wait for a busy replica (PR #274).**
   - The new `[chat_gateway]` option `admission_wait_seconds` (default `0`,
     the previous fail-fast behaviour) lets a request wait that long for a
     busy replica. `max_admission_waiters` (default `16`) bounds how many
     requests wait.
   - Overload 429s now carry `Retry-After: 1`.
   - Why it matters: a rejected admission creates no Job, so retrying is safe.
     OpenCode's title request no longer turns every new session's main request
     into a 429 on single-replica profiles.
   - Keep `admission_wait_seconds + stream_keepalive_seconds` below the read
     timeout of any proxy in front of the Gateway.

## Production evidence (operator site, 2026-11-17)

The integrated source runs in the maintainer's production site. This
evidence covers that site only; it is not a universal qualification.

| Host | Profile | Runtime | Build |
| --- | --- | --- | --- |
| Control | Gateway + scheduler, `admission_wait_seconds = 120` | — | main `92f023d` |
| spica | `qwen3.6-35b-a3b`, 64K | Strata 0.2.13.1 | main `92f023d` |
| deneb | `qwen3.6-35b-a3b-short`, 12K | Strata 0.2.13.1 | main `92f023d` |
| sirius | `qwen3.6-35b-a3b-fast`, 196608 | llama.cpp, KV `q8_0` | main `92f023d` |

Streamed 300 tokens through the public endpoint:

| Profile | rc.1 | rc.2 |
| --- | --- | --- |
| `qwen3.6-35b-a3b-fast` (sirius) | 31.8 s | 5.4 s |
| `qwen3.6-35b-a3b-short` (deneb) | 29.6 s | 15.0 s |
| `qwen3.6-35b-a3b` (spica) | — | 17.3 s |

OpenCode 1.18.35 runs against the same endpoint:

- **Long answer:** 2048 tokens arrived in 29 s on the fast profile. With rc.1
  nothing had arrived after 40 s.
- **Concurrent sessions, 64K:** three concurrent file-reading sessions all
  answered correctly.
- **Concurrent sessions, 12K:** three concurrent sessions that each read a
  file larger than the window no longer failed as busy. OpenCode recognised
  every overflow and compacted.
- **Limit that remains on 12K:** a single tool result larger than 12K tokens
  still cannot fit after compaction. Use the 64K or 192K profile for large
  files.

Embedding and decision Workers stayed on the `v0.1.x` builds and are
unaffected.

  PRs #238 and #241–#246.

  from streaming, but connection pooling is still open.

## Operational boundaries

- PostgreSQL 17 migrations `000`–`005` are unchanged since v0.1.3. No
  migration runs at release time.
- `admission_wait_seconds` is off unless configured.
- Publishing the tag or the GitHub Release does not update running services,
  credentials, model downloads or GPU ownership. Site rollout still needs an
  explicit operator GO with a rollback path.
- Historical release notes stay byte-for-byte unchanged. The release-version
  alignment tests pin them by SHA-256.

## Remaining publication steps

1. Merge the release PR and wait for the merge commit's CI to pass.
2. Build the wheel, sdist and source archive from the exact merge commit, and
   write `RELEASE-MANIFEST.txt` and `SHA256SUMS`.
3. Create the annotated prerelease tag `v0.2.0-rc.2` and publish the GitHub
   prerelease with those assets.
4. Promote to `v0.2.0` GA by changing version metadata only, after the
   maintainer accepts the candidate.
