# TSUMGI v0.3.0-rc.1 — Runtime Rename Candidate

> **Pre-release candidate, not stable GA.** This note describes the proposed
> prerelease scope. The release is published only once the annotated Git tag
> and the GitHub Release assets (`RELEASE-MANIFEST.txt`, `SHA256SUMS`) are
> verified. A public prerelease does **not** upgrade any installed Control,
> Worker, GPU runtime, PostgreSQL schema or site configuration.

## Version identity

| Surface | Intended identity |
| --- | --- |
| Git tag | `v0.3.0-rc.1` — annotated prerelease |
| Python distribution | `tsumgi==0.3.0rc1` |
| Nix Control, Worker, Installer and integration packages | `0.3.0pre1` (sorts before `0.3.0` GA) |
| Prior stable | Published `v0.2.1` (2026-11-17) |
| Candidate functional baseline | The integration branch `rename/0.3.0` merged to `main` (includes everything on `main` through PR #293 and the rename PRs #282–#290 and #294) |
| Tagged identity and checksums | The release manifest and `SHA256SUMS` of the exact tag establish the published source and artifacts |

## Why the minor version changes

The candidate renames the runtime from `astrumweaver` to `tsumgi`, including the
names clients and hosts depend on. In the 0.x series that incompatibility is
signalled by the minor version, so the next release is `0.3.0`.

## Breaking changes

An installed host moves with the host migration tool; it does not upgrade in
place by hand. See [Moving a host](../host-migration.md) and the
[cutover plan](../design/rename-cutover-plan.md).

| Area | Before | Now |
| --- | --- | --- |
| Python distribution and import package | `astrumweaver` | `tsumgi` |
| Console commands | `astrumweaver-*` | `tsumgi-*` |
| NixOS options and flake outputs | `services.astrumweaver.*`, `.#astrumweaver` | `services.tsumgi.*`, `.#tsumgi` |
| systemd units, users and groups | `astrumweaver-control.service`, `astrumweaver-worker.service`, `astrumweaver`, `astrumweaver-control`, `astrumweaver-config` | `tsumgi-control.service`, `tsumgi-worker.service`, `tsumgi`, `tsumgi-control`, `tsumgi-config` |
| Paths | `/etc/astrumweaver`, `/var/lib/astrumweaver*`, `/opt/astrumweaver`, `/usr/local/libexec/astrumweaver`, Nix profiles `astrumweaver-*` | the same with `tsumgi` |
| Environment variables | `ASTRUMWEAVER_*` | `TSUMGI_*` |
| Client API | `x_astrumweaver` response object; `x_astrumweaver_input_type`, `x_astrumweaver_embedding_space_id` request fields; object types `astrumweaver.decision`, `astrumweaver.decision_profile`, `astrumweaver.embedding_space` | `x_tsumgi`, `x_tsumgi_input_type`, `x_tsumgi_embedding_space_id`, `tsumgi.*` |
| Decision operation schema | `astrumweaver-decisions-v1` | `tsumgi-decisions-v1`: the decision serving contract gets a new revision, so the decision catalog and the decision Worker's serving declaration must be re-pinned (`tsumgi-repin-decision`). Chat and embedding contracts do not contain the name; their pins are unchanged |
| Evidence field | `astrumweaver_revision` | `tsumgi_revision` |
| Setup helper for older helper versions | in-place upgrade of reviewed pre-rename GPU mapper v59 | removed; hosts move with the migration tool |

The code reads only the new names. A search of the maintainer's repositories
found no client outside this repository that reads or sends the old API names.

## Integrated changes since v0.2.1

1. **Runtime rename (#120 Phase B, PRs #282–#287, #289–#290, #294).** The names above,
   with the plan, the audit of what the rename touches, and a documented cutover.
   See [design/rename-phase-b.md](../design/rename-phase-b.md).
2. **`tsumgi-migrate-host` (PRs #285, #287).** Moves one Worker or Control host from
   the old names: stops the unit, renames users and groups in place (same uid/gid),
   moves the directories and Nix profiles, retargets absolute symlinks, rewrites
   names inside configuration and units, and starts the new unit. It writes a
   rollback script and a backup first, refuses files that carry a pinned identity,
   and never edits a Nix store path or a secret value. Control is held until the
   database has been renamed.
3. **`tsumgi-repin-decision` (PR #290).** Writes the re-pinned decision serving
   declaration, decision catalog and runtime manifest, loading each back through
   the classes the Worker and Control use. The heavy CUDA llama.cpp build keeps its
   previous store-path name on purpose, so a host that already holds it does not
   recompile it.
4. **Operator console (PRs #279–#281).** A read-only console served by Control
   (`[admin_ui] enabled = true`) with Worker status, GPU telemetry from the Workers
   and a Hugging Face model check. HTTP Basic authentication with a first-run setup
   page that needs a one-time code, throttled failures, and `trusted_proxies`.
   Default off. See [operator console](../admin-console.md).
5. **Audio source series (opt-in, default off; PRs #286, #288, #260, #291–#293).**
   Orphaned WAV recovery under exclusive Control spool ownership; explicit manifests
   for the owned VOICEVOX Worker and a Style-Bert-VITS2 (JVNV) Worker; a Parakeet
   Japanese STT Worker manifest; Control audio epoch revocation (negative-only) and
   an epoch preparation slice; per-Worker authentication; a VOICEVOX offline bundle;
   an offline STT comparison scorer; and an operator-only local VOICEVOX preview.
   **No audio engine is qualified, enabled by default, or covered by the release
   guarantee.** Epoch preparation has no release path yet (a prepared Worker stays
   out of registration and claims) and must not be enabled.
6. **Closed as not planned (#237, #240; PRs #238, #241–#246).** Bounded native
   llama.cpp shutdown and cgroup containment, with the conditions for reopening
   recorded in the issues.

## Rehearsal evidence (operator site, 2026-11-19)

This evidence covers the maintainer's site only. **The rename has not yet been
cut over in production.**

- `tsumgi-migrate-host` was run for real on one lent 64K Worker host (users,
  groups, directories, units, profiles, symlinks): a new-build Worker joined the old
  Control, loaded its model and took its share of streaming requests next to three
  old-name replicas; the rollback took 5.6 s and a second round trip left mode,
  owner, type and link target of 55 entries identical. The rehearsal also found, and
  this candidate fixes, a rollback that lost file owners.
- A new-build Control started against a renamed copy of the production database;
  its chat profile revisions equalled production's, the embedding catalog loaded
  unchanged, the old decision catalog was refused and the re-pinned one loaded.
- The operator console, with its authentication, has served the production Control
  since 2026-11-19.
- Not rehearsed: the decision Worker serving with the re-pinned files, and a full
  Control cutover.

## Operational boundaries

- PostgreSQL 17 migrations `000`–`005` are unchanged since v0.2.1. This release adds
  `006_audio_epoch_fences.sql` and `007_audio_epoch_preparations.sql` (new tables
  only). A Control built from this release refuses a database that is not at `007`,
  so `tsumgi-migrate` runs before it starts; the previous Control ignores migrations
  it does not know.
- The PostgreSQL acceptance tests for the audio slices require a PostgreSQL 17
  server and skip as `NOT_VERIFIED` on any other major version; CI does not run them.
- Publishing the tag or the GitHub Release does not update running services,
  credentials, model downloads or GPU ownership. Site rollout still needs an
  explicit operator GO with a rollback path.
- Historical release notes stay byte-for-byte unchanged and still use the old
  names. The release-version alignment tests pin them by SHA-256.

## Not included, carried over

- Cleanup and activation of audio epoch preparation, and any enabling of it.
- Qualification of any audio engine, voice rights, and real-audio acceptance (#173,
  #175–#181, #215, #216, #247).
- FreeToken follow-ups #262 items 1–3; #148 and #149 are on hold.

## Remaining publication steps

1. Merge the release PR and wait for the merge commit's CI to pass.
2. Build the wheel, sdist and source archive from the exact merge commit, and
   write `RELEASE-MANIFEST.txt` and `SHA256SUMS`.
3. Create the annotated prerelease tag `v0.3.0-rc.1` and publish the GitHub
   prerelease with those assets.
4. Cut the production over with the [cutover plan](../design/rename-cutover-plan.md)
   (owner approval and a time window), then promote to `v0.3.0` GA by changing
   version metadata only, after the maintainer accepts the candidate.
