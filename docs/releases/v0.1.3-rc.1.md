## Reviewed integrated changes since v0.1.2

This is a **patch-number increment at the maintainer's request**, not a
claim that all integrated changes are defect fixes. The source also includes
explicitly opt-in audio API and Worker integration work, some of which is
not yet qualified for default/general runtime serving.

1. **Chat and OpenCode compatibility ([#209](https://github.com/upiscium/TSUMGI/issues/209) / [PR #211](https://github.com/upiscium/TSUMGI/pull/211)).**
   Restore real OpenCode 1.18.35 request admission by validating a reviewed
   `reasoning_effort` hint (`low`/`medium`/`high`; explicitly **no
   runtime reasoning-budget effect**) and losslessly normalizing bounded,
   text-only user content parts. Other fields/media, invalid tool history,
   `store:true`, and request-size violations remain fail-closed.
   Candidate and subsequently deployed production Control qualified real
   OpenCode plain + read-tool roundtrips with Qwen3.8-27B and Bonsai2-27B
   (**4/4**) plus negative HTTP cases (**9/9**). Global OpenAI-oriented
   `plan` agent overrides can exceed the smaller local model's context;
   that separate configuration issue is tracked in
   [dotnix #68](https://github.com/upiscium/dotnix/issues/68).
2. **Bounded audio artifact handling ([#174](https://github.com/upiscium/TSUMGI/issues/174)).**
   Job/attempt-scoped private spool, bounded WAV transfer, output cleanup,
   staged input and recovery/fault tests. Opt-in configuration and existing
   authenticated/fenced Job semantics are preserved; this is not general
   media storage, public object serving, or automatic long-term retention.
3. **Speech/transcription API groundwork ([#175](https://github.com/upiscium/TSUMGI/issues/175)).**
   Validated voice catalog, bounded speech/recognition HTTP contracts and
   providerless durable Job ingress. An API route does not by itself
   guarantee that a corresponding model/voice runtime is installed.
4. **Opt-in Control/Worker audio integration ([#180](https://github.com/upiscium/TSUMGI/issues/180)).**
   Source-merged Control audio routes, Nix/systemd setup/spool stages,
   Serving feature gates, Worker media transfer/executor bridge and
   reviewed setup selection. A future native managed audio runtime is
   separately qualified, not enabled by default in this RC.
5. **VOICEVOX and Style-Bert-VITS2 source adapters
   ([#176](https://github.com/upiscium/TSUMGI/issues/176),
   [#177](https://github.com/upiscium/TSUMGI/issues/177)).**
   Reviewed, pinned adapter contracts deliberately fail closed for
   unqualified Serving features. Owned ManagedRuntime readiness,
   inference/process integration and actual Japanese-language production
   audio acceptance remain open
   ([#214](https://github.com/upiscium/TSUMGI/issues/214),
   [#215](https://github.com/upiscium/TSUMGI/issues/215),
   [#216](https://github.com/upiscium/TSUMGI/issues/216),
   [#181](https://github.com/upiscium/TSUMGI/issues/181)).

The release includes **only changes already merged** into the pinned source
baseline, plus bounded Python/Nix version metadata, this note, README and
release-alignment tests. Unmerged follow-up implementations are not
represented as included.

## Compatibility and non-goals

- Technical `astrumweaver` Python imports, command names, environment
  variables and service names are retained during the TSUMGI naming transition.
- Existing PostgreSQL migration files `000`–`005` are unchanged
  since published `v0.1.2`. Release publication requires **no migration**.
  Durable Job/media retention and cleanup semantics must not be inferred
  merely from an accepted `store:false` option.
- Qwen3.8/Bonsai runtime packages remain explicitly separate opt-in
  artifacts; do not distribute models, NVIDIA drivers or private metadata.
- No full VOICEVOX, Style-Bert-VITS2 or Japanese STT deployment,
  long-running voice quality/latency certification, blanket OpenAI API
  compatibility, PyPI publication, native hostile same-UID isolation,
  fleet rollback, GPU universality, 24-hour soak or uptime SLA is claimed.
- Existing installed Control/Worker profiles stay at their explicitly
  approved commits. A release tag alone does **not** upgrade the Home Lab.
  Site upgrades and rollbacks require their own operator go/no-go.
- A stable `v0.1.3` GA needs a separate RC qualification decision,
  reviewed stable-version promotion, exact-tag artifact verification and
  explicit publication authorization.

## RC publication gates

- Independent source/security review of the exact candidate change set.
- Complete Python/PostgreSQL regression and version-alignment tests
  against the pinned candidate, not historical main.
- GitHub CI `unit` and `nix` GREEN on the exact merged candidate commit,
  generated NixOS first-run checks and immutable
  `#control`, `#worker`, `#installer`, `#integration` builds.
  Optional Qwen3.8/Bonsai runtime package qualification must be recorded
  as executed or explicitly scoped as deferred, not assumed.
- Wheel, Python source distribution and Git source archive built from
  the exact tag commit; inspect package metadata, migrations and contents,
  check reproducibility and create matching `RELEASE-MANIFEST.txt` and
  `SHA256SUMS`.
- Publish with GitHub **prerelease** flag, never stable/latest, and read
  back the tag, asset digests and release identity. No installed service
  restart, model replacement, migration or profile switch.
