## New opt-in capability

- Support one explicitly qualified model, **PrismML Ternary-Bonsai-2-27B-PQ2_0 GGUF**, from revision `b072e1d3b35a0a630cece372c2127528e0994386`. Verified model SHA-256: `3907dc1658db1f78a9826bf8d5bcb8dc65db0d466388937af57f2294fae62ec1`. Size 7,206,168,928 bytes.
- Isolated Nix `#runtime-bonsai-llama-cpp` package and profile, pinned to PrismML `llama.cpp` native source `e8fd209c975c80aa7fb36a8423571ff3b1b7e955`. No change to the default upstream `#runtime-llama-cpp` path.
- The provider must opt in with `runtime_flavor=bonsai2-pq2`, single GPU, VRAM-only model placement, Jinja structured Tool Calls, native `--reasoning off`, Context at least 8,192 and verified GGUF bytes before owned native startup.
- Pascal/GTX1080Ti CUDA driver compatibility fix from [#159](https://github.com/upiscium/TSUMGI/pull/159): provide matching NVIDIA PTX JIT compiler/NVVM alongside the host CUDA driver in a private limited-library bridge. Not a promise that every GPU/driver combination works.
- Generic-systemd Installer's Bonsai and upstream Nix runtime profiles remain separate; Nix version and package hash are reviewable. Native process secrets are *not* isolated from a compromised peer sharing the same Worker UID.
- Preserve technical `astrumweaver` Python import, service CLI, environment and persistent technical identifiers for compatibility.

## Field-test evidence and limits

- 2026-10-19, independent production host **deneb** and **spica**: pinned-model full SHA-256 verified, both Bonsai Workers Ready/Online and GPU native runtime in active service. Existing GA rollback units/profile retained.
- An actual immutable serving-bound `llm.chat` Job was admitted through Control/PostgreSQL and constrained to each exact GPU UUID. Each Job used exactly one attempt, traversed `queued → running → succeeded`, returned an expected response marker and recorded the correct assigned host:
  - deneb `8a8b81ee-048f-444c-9302-52129b7275e6`;
  - spica `338c78f4-317d-4f8c-8968-3f72c422bc92`.
- Earlier Nix native, OpenCode Coding Agent one-file and multi-file E2E, cancellation and rollback evidence: [Bonsai support issue #154](https://github.com/upiscium/TSUMGI/issues/154), [deployment #156](https://github.com/upiscium/TSUMGI/issues/156), merged [PR #155](https://github.com/upiscium/TSUMGI/pull/155), merged [PTX fix #159](https://github.com/upiscium/TSUMGI/pull/159).
- **Important evidence boundary:** the above describes deployed main-line feature tests. The actual `v0.1.1-rc.1` release **artifacts** and an installed RC profile must be rebuilt and smoke-tested at their exact future tagged commit; this document is not that evidence.

## Known restrictions

| Topic | Known boundary |
| --- | --- |
| Models | Only Bonsai 2 **27B PQ2_0** is supported; no generic Bonsai, PQ/TQ format support or automatic model download |
| GPU placement | Initial qualification targets **one GTX1080Ti 11GB GPU** per Worker; VRAM availability is checked fail-closed, not reserved against arbitrary external actors |
| CPU/native security | Trusted/private LXC assumption, no hostile same-UID or internet-exposed native service guarantee ([#149](https://github.com/upiscium/TSUMGI/issues/149)) |
| Model/runtime version | Native PrismML fork is separate from normal upstream llama.cpp; model/runtime are pinned, not hot-swapped |
| Load & memory | Bounded tests are not 24-hour full-saturation reliability or a universally established latency SLA ([#150](https://github.com/upiscium/TSUMGI/issues/150)) |
| Worker reconnection | After a lost Control acknowledgement, a Worker may remain Offline with fresh Heartbeats until an explicit safe registration; production altair was restored by restarting an idle Worker ([#162](https://github.com/upiscium/TSUMGI/issues/162)). Do not auto-resurrect stale lease owners |
| Qwen3.8 upstream packaging | Separate source PR [#158](https://github.com/upiscium/TSUMGI/pull/158), **not included** in this RC unless that PR is separately merged and qualified |
| Release publication | Source tag, actual Release assets and any model-site migration are independent approvals; no automatic production restart |

## RC validation checklist

1. Validate exact release commit, Nix lock/source, Python and Nix package versions. All intended source changes must be merged or explicitly included; exclude unrelated unmerged PRs.
2. Run complete Python regression, CI `unit`/`nix`/Security jobs, generated NixOS config check and Nix builds for Control, Worker, Installer and both upstream/Bonsai runtime outputs.
3. Generate the wheel and source archive from the immutable RC commit, verify package metadata, artifact checksums and source provenance. Do not guess their hashes.
4. Install and rollback the **actual release package** into a separate Nix profile on an authorized test Worker; prove no impact to the existing GA profile.
5. Execute one actual bounded `Control → PostgreSQL → Worker → Bonsai Native GPU → OpenCode/Chat` test, including Tool Call, cancellation, restart and resource release. Confirm fail-closed mismatched model hash and wrong GPU.
6. Publish `v0.1.1-rc.1` and GitHub Release only with explicit maintainer approval. Operators separately approve any site deployment.
7. Promote to `v0.1.1` only after RC artifact-specific results, independent review, rollback acceptance and observed field operation; the GA artifact needs its own exact-source check.

## Installation and rollback

See [Bonsai Runtime documentation](../bonsai-llama-cpp.md) and [Operator rollout/rollback gates](../operator-rollout-gates.md). Prepare a separately pinned Nix installer/profile; retain your installed `v0.1.0` profile, database backup and model files. A release tag does not migrate PostgreSQL, replace Worker credentials, allocate GPU hardware or update services.

Nix `0.1.1pre1` is intentionally prerelease and sorts after `0.1.0` but before future `0.1.1`; do not infer that blindly upgrading an arbitrary older Nix profile is safe.
